The Call Stack: Mechanics from First Principles

push, pop, call, ret — how the CPU saves and restores rip to enable function calls, where local variables live, and why the stack is the primary target of memory-corruption exploits.

Prerequisites — Modules 01–06 complete: registers solid, memory sections understood, conditional jumps fluent.

What You Will Build

  • stack.asm — demonstrates push/pop byte mechanics, the call/ret mechanism, stack frame setup/teardown, local variables at rbp-offsets, and three levels of nested calls with live rsp addresses
  • A clear mental model of the call stack layout that enables you to read crash dumps, write exploits, and understand GDB backtraces

What Is the Stack?

The stack is a region of ordinary RAM. There is nothing physically special about it. What makes it "the stack" is the CPU register rsp (the Stack Pointer), which always points to the topmost used byte. By convention, the stack grows downward — each new piece of data pushed onto the stack lives at a lower address than the previous one. On a modern Linux process, the stack typically starts at an address near the top of virtual memory (around 0x7fffffffe000) and grows toward lower addresses as functions call each other.

The stack has two roles that cannot be separated: it stores return addresses (so ret knows where to go back to) and local variables (data that only exists while a function is active). These two roles sharing the same memory region is what makes buffer overflows so dangerous — a local variable that overflows its bounds can overwrite the return address sitting right next to it.

push and pop: The Physical Mechanics

; push VALUE  is exactly equivalent to:
sub  rsp, 8          ; grow the stack (move rsp down by 8 bytes)
mov  [rsp], VALUE    ; write value at the new top of stack

; pop DEST  is exactly equivalent to:
mov  DEST, [rsp]     ; read value from top of stack into DEST
add  rsp, 8          ; shrink the stack (move rsp up by 8 bytes)
Tip — "Popped" data is not erased
After pop rbx, the bytes that were at [rsp-8] are still there in RAM — they just live below the new rsp. The convention is that anything below rsp is "dead" (may be overwritten at any time), but the bytes aren't zeroed. This is why stack memory can leak sensitive data: a function that doesn't zero its local buffer before returning leaves that data accessible until the next function clobbers it.

call and ret: Saving and Restoring rip

; call LABEL  is exactly equivalent to:
push <address of next instruction>   ; save return address
jmp  LABEL                            ; transfer control

; ret  is exactly equivalent to:
pop  rip                              ; load return address into rip
; (you cannot write "pop rip" directly — ret is the only way)
The Core of Every Stack Exploit
ret unconditionally trusts whatever 8 bytes are at [rsp] and jumps to that address. It performs no validation. If an attacker can write an arbitrary 64-bit value to [rsp] at the moment ret executes — either by overflowing a local buffer or by other means — they control rip. This is the foundational primitive of stack-based exploitation. Module 18 demonstrates this live with GDB.

The Standard Stack Frame

Every function that uses the stack (has local variables or calls other functions) follows a prologue/epilogue pattern. This creates a frame — a region of the stack dedicated to that function's data.

; === PROLOGUE — runs at function entry ===
my_function:
    push rbp          ; save the CALLER's frame base pointer
    mov  rbp, rsp    ; OUR frame base = current top of stack
    sub  rsp, 32     ; allocate 32 bytes for local variables
                      ; rsp must stay 16-byte aligned!

    ; Local variables live here:
    ; [rbp - 8]  = first  local (8 bytes)
    ; [rbp - 16] = second local (8 bytes)
    ; [rbp - 24] = third  local (8 bytes)
    ; [rbp - 32] = fourth local (8 bytes)

    ; ... function body ...

; === EPILOGUE — runs before ret ===
    add  rsp, 32     ; release local variable space
    pop  rbp          ; restore caller's rbp
    ret               ; pop return address → rip

; Shorthand for the epilogue: "leave" = add rsp,(rbp-rsp) + pop rbp
    leave
    ret

Stack Frame Memory Layout

At any point inside my_function (after the prologue), the stack looks like this:

higher addresses ↑... caller's frame ...
[rbp + 8]return address (saved rip from call)← ret reads here
[rbp + 0]saved caller rbp← rbp points here
[rbp - 8]local variable 1
[rbp - 16]local variable 2
[rbp - 32]local variable 4← rsp points here
lower addresses ↓... next call's frame goes here ...
Security Insight — The Return Address Is Adjacent to Locals
Notice that the return address lives at [rbp+8] and local variable 1 lives at [rbp-8]. They are separated by only 16 bytes (the saved rbp + one local). A buffer overflow that writes past the end of local variable 1 in the upward direction (toward higher addresses) will eventually overwrite the saved rbp and then the return address. Module 18 exploits exactly this layout.

16-Byte Stack Alignment

The System V AMD64 ABI (Linux/macOS) and the Microsoft x64 ABI (Windows) both require that rsp must be aligned to a 16-byte boundary at the moment of any call instruction. SIMD instructions (movaps, movdqa) and some library functions will crash with a General Protection fault (#GP) if rsp is misaligned.

The rule: after entering a function, rsp is aligned to 8 (not 16) because call pushed an 8-byte return address. Your prologue's push rbp adds another 8 bytes — now aligned to 16 again. Then you must subtract a multiple of 16 from rsp to maintain alignment while allocating local space.

; After call: rsp = 0x...X8 (8-byte aligned, not 16)
push rbp       ; rsp -= 8 → now 16-byte aligned (rsp = 0x...X0)
mov  rbp, rsp
sub  rsp, 32   ; 32 is a multiple of 16 → rsp still 16-byte aligned
; NEVER: sub rsp, 24  (would misalign to 8-byte boundary)

Exercises

Warm-up

1. Count the bytes per frame

From the output above, compute the exact byte difference between each rsp level. It should match: push rbp (8) + sub rsp, 16 (16) + call pushes return address (8) = 32. Verify this arithmetic matches the assembly code.

Core

2. Read the stack in GDB

Break at level_c and run x/16gx $rsp. Identify each 8-byte slot: the local variable (0xCCCC...), the saved rbp of level_c, the return address from level_b, the saved rbp of level_b, and so on. Match each address to the code. This is exactly how you analyse crash dumps.

Core

4. Write a recursive factorial

Implement factorial(n) in assembly: if rdi == 0 return 1, else return rdi * factorial(rdi-1). Remember to save rdi on the stack before the recursive call (push it as a local variable), because the recursive call will clobber rdi. Test with factorial(10) = 3628800.

Stretch

5. Manually walk the frame chain

Inside GDB at level_c, use x/2gx $rbp to read the saved rbp and return address. The saved rbp points to level_b's frame. Use that value to read level_b's saved rbp and return address: x/2gx <saved_rbp_value>. Continue until you reach main's frame. Compare with the backtrace output.
