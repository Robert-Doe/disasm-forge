Inline Assembly & Reading Compiler Output

Two complementary skills: embedding assembly inside C with GCC's asm volatile constraint syntax, and reading the assembly that the compiler emits at -O2 to recognize optimization patterns — strength reduction, cmov, tail-call elimination, and auto-vectorization.

Prerequisites — All prior modules. This module ties together instruction knowledge (Modules 04–06), ABI (Module 09), and addressing (Module 10) in a C-integrated context.

What You Will Build

  • inline_asm.c — GCC extended inline assembly: addq, mulq (128-bit), bswap, rol, cpuid, rdtsc, pushfq
  • inline_asm_O2.s (generated) — compiler output to read and annotate

GCC Extended Inline Assembly Syntax

asm volatile (
    "assembly template"
    : output operands
    : input operands
    : clobber list
);

The Four Parts

  • Template — the instruction string, with operand placeholders %0, %1, …
  • Outputs — "constraint"(C_variable) pairs telling the compiler where to put results. Constraints start with = (write-only) or + (read-write).
  • Inputs — "constraint"(expression) pairs telling the compiler where to put arguments.
  • Clobbers — registers and/or "memory" that the snippet modifies without being listed as outputs. The compiler must save/restore clobbered registers.

Common Constraint Letters

ConstraintMeaning
"r"Any general-purpose register
"a"rax/eax/ax/al specifically
"d"rdx/edx/dx/dl specifically
"c"rcx/ecx/cx/cl specifically (required for shifts/rotates)
"m"Memory operand (any valid addressing mode)
"i"Immediate (compile-time constant)
"0"–"9"Same register as the Nth output operand (tied constraint)
"=r"Write-only, any register
"+r"Read-write, any register

Example: 128-bit Multiply via mulq

/* mulq writes the full 128-bit product into rdx:rax */
static void mul_wide(uint64_t a, uint64_t b, uint64_t *hi, uint64_t *lo) {
    uint64_t h, l;
    asm volatile (
        "mulq %3"
        : "=d"(h),     /* rdx → h  */
          "=a"(l)      /* rax → l  */
        : "a"(a),      /* rax ← a  */
          "r"(b)       /* any reg ← b  */
        :
    );
    *hi = h;  *lo = l;
}
Tied Constraints — "0" through "9"
When an output and an input must use the same register (e.g. add rax, rbx where rax is both input and output), use a numeric constraint on the input referring to the output's position: : "=r"(result) : "0"(a), "r"(b). This tells the compiler "put a in the same register as result, then the add modifies it in place."

Hardware Intrinsics via Inline Asm

CPUID — CPU Feature Detection

uint32_t a, b, c, d;
asm volatile (
    "cpuid"
    : "=a"(a), "=b"(b), "=c"(c), "=d"(d)
    : "a"(leaf), "c"(0)   /* leaf → eax, subleaf → ecx */
    :
);
/* Vendor string: 12 chars from ebx, edx, ecx */
char vendor[13] = {0};
memcpy(vendor+0, &b, 4);
memcpy(vendor+4, &d, 4);
memcpy(vendor+8, &c, 4);

RDTSC — Cycle Counter

uint32_t lo, hi;
asm volatile (
    "rdtsc"
    : "=a"(lo), "=d"(hi)
    : :
);
uint64_t cycles = ((uint64_t)hi << 32) | lo;

Reading Compiler Output at -O2

Generate the assembly with make asm-O2 (produces inline_asm_O2.s), then look for these patterns:

C source

uint64_t multiply_by_5(uint64_t x) {
    return x * 5;
}

gcc -O2 output

multiply_by_5:
  leaq (%rdi,%rdi,4), %rax
  ret

C source

int64_t absolute_value(int64_t x) {
    return x < 0 ? -x : x;
}

gcc -O2 output

absolute_value:
  movq  %rdi, %rax
  negq  %rax
  cmovns %rdi, %rax
  ret

C source

int64_t divide_by_8(int64_t x) {
    return x / 8;
}

gcc -O2 output

divide_by_8:
  movq  %rdi, %rax
  sarq  $63, %rax   ; sign-extend to all 1s or 0
  shrq  $61, %rax   ; bias = 7 for division by 8
  addq  %rdi, %rax
  sarq  $3, %rax    ; arithmetic right-shift by log2(8)
  ret
Why the signed division trick?
C's signed integer division truncates toward zero. But arithmetic right shift truncates toward negative infinity. For negative numbers these differ: -7 / 8 = 0 in C, but -7 >> 3 = -1. The compiler adds a bias: x + (x >> 63 & 7) before shifting. The sarq $63 produces 0 for non-negative, -1 (all ones) for negative. ANDing with 7 gives the bias. This is one of the most commonly misread patterns in optimized disassembly.

Exercises

Warm-up

1. Inline asm for POPCNT

Write a C function uint64_t popcount_asm(uint64_t x) using inline asm with the popcnt instruction. Use "=r" for output and "r" for input. Verify it returns the same result as __builtin_popcountll(x) for several inputs. Then compile with -O2 -S and find the popcount_asm function — it should be just two instructions (popcnt + ret).

Core

2. Annotate the compiler's sum_array output

Run make asm-O2 and find the sum_array function in inline_asm_O2.s. Annotate every instruction with a comment explaining what it does. You should see: loop setup, possibly an SSE/AVX vectorized body (look for xmm or ymm registers and paddq/vpaddq), a scalar cleanup loop for remaining elements, and a horizontal reduction to combine vector lanes into the final sum. This is what your Module 13 SIMD work looks like when a compiler does it automatically.

Stretch

3. CPUID feature flags decoder

Extend inline_asm.c to decode the feature flags from CPUID leaf 1 (set eax=1). The output is in ecx and edx. Key bits: ecx bit 19 = SSE4.1, ecx bit 20 = SSE4.2, ecx bit 25 = AES-NI, ecx bit 28 = AVX, edx bit 26 = SSE2. Print a formatted table showing which features your CPU supports. This is how libc implementations select the fastest code path at runtime, and how security tools detect hardware-backed AES for cipher selection.
