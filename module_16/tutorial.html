Linker & Loader Internals

Object files contain unresolved references — placeholders with relocation entries. The linker collects all object files, resolves every symbol to an address, patches the placeholders, and writes the final binary. The dynamic loader repeats this for shared libraries at runtime.

What is a Relocation Entry?

When the assembler encounters call b_add, it does not know where b_add will live — that depends on the final link order. So it writes zeros (or a placeholder) into the call instruction's target field and records a relocation entry:

; In a.o's relocation table:
; Offset    Type        Symbol     Addend
; 0x3A      R_X86_64_PC32  b_add    -4
;           ↑              ↑        ↑
;     byte in a.o       symbol   adjustment for PC-relative

When the linker runs, it:

  1. Scans all .o files, collects every defined symbol and its address in the final layout
  2. Scans all undefined references (relocations) and matches them to definitions
  3. Writes the correct address into each relocation slot in the output binary

Seeing Relocations with objdump

$ make && make relocs
=== Relocations in a.o === RELOCATION RECORDS FOR [.text]: OFFSET TYPE VALUE 0000000000000047 R_X86_64_PC32 b_add-0x0000000000000004 000000000000005b R_X86_64_PC32 b_counter-0x0000000000000004 000000000000007a R_X86_64_PC32 a_multiply-0x0000000000000004 ... === Relocations in b.o === RELOCATION RECORDS FOR [.text]: OFFSET TYPE VALUE 0000000000000039 R_X86_64_PC32 a_multiply-0x0000000000000004
R_X86_64_PC32 — PC-relative 32-bit relocation
This is the relocation type for call and jmp instructions in 64-bit x86. The CPU encodes the target as a signed 32-bit offset from the next instruction's address (Program Counter relative). The linker computes: patch_value = symbol_address - (relocation_offset + 4). The -4 addend in the relocation record accounts for the 4-byte encoding of the offset itself. All this is why near calls can only reach ±2 GB from the call site — the 32-bit signed displacement limit.

extern and global in NASM

; In a.asm:
extern b_add        ; "I reference this symbol — linker must find it elsewhere"
global a_multiply   ; "I define this symbol — export it for other units"

; In b.asm:
extern a_multiply   ; references a.asm's export
global b_add        ; satisfies a.asm's extern declaration

PLT and GOT — Dynamic Linking at Runtime

When your binary calls a shared library function (like printf), the linker cannot know the final address — it depends on where libc.so is loaded in memory (randomized by ASLR). Instead it creates two structures:

  • PLT (Procedure Linkage Table) — a stub in your binary's .plt section. Every call to printf actually calls printf@plt.
  • GOT (Global Offset Table) — a table of 8-byte pointers in .got.plt. Initially these point back into the PLT resolver. After the first call, the dynamic linker patches the GOT entry to point directly at the real function.
; First call to printf — what actually executes:
; 1. call printf@plt  →  jumps to [got.plt entry for printf]
; 2. GOT entry initially contains: address of plt resolver stub
; 3. Resolver calls _dl_runtime_resolve(link_map, reloc_index)
; 4. Dynamic linker finds printf in libc.so, writes real address into GOT
; 5. Execution jumps to real printf
;
; Second call to printf:
; 1. call printf@plt  →  jumps to [got.plt entry for printf]
; 2. GOT entry now contains real printf address → direct jump
Security — GOT Overwrite Attacks
The GOT is a writable table of function pointers in the process's data segment. If an attacker can write an arbitrary 8-byte value to a GOT entry (via a buffer overflow, format string write, or use-after-free), the next call to that library function jumps to the attacker's address. This is the basis of GOT overwrite exploitation — a classic technique for turning an arbitrary-write primitive into code execution. Modern mitigations: RELRO (RELocation Read-Only) marks the GOT read-only after the dynamic linker finishes resolving symbols (-z relro -z now), preventing this class of attack.

Exercises

Warm-up

1. Verify relocation patching with GDB

Build with make, then run gdb ./link_demo. Break at main, then disassemble main. Find the call b_add instruction. Note its address and the 4-byte relative displacement encoded in the instruction bytes. Manually compute call_site_address + 4 + displacement and verify it equals the address shown by info address b_add. This is the exact arithmetic the linker performed when patching the relocation.

Core

2. Create a local-only function (no global)

Add a function b_internal_helper to b.asm without declaring it global. Call it from b_add. Build, then run nm link_demo | grep b_internal — it will appear with lowercase t (local). Now try to call b_internal_helper from a.asm (with extern b_internal_helper) and observe the linker error: "undefined reference." This demonstrates that symbol visibility, not physical location, determines linkability.

Stretch

3. Trace PLT/GOT lazy resolution with GDB

Add a printf("hello\n") call in link_helper.c. Build, then run under GDB. Before calling printf, inspect x/2gx 0x<got_entry_for_printf> (find the address via objdump -R ./link_demo | grep printf). Step through the first call and watch the GOT entry change from the PLT resolver address to the real printf address in libc.so. After the first call completes, inspect the GOT entry again — it now points directly into libc. This is lazy binding in action.
