Reading Disassembly & Reverse Engineering Patterns

The direction reverses. Four stripped, optimized binaries wait for analysis — no source, no symbols. You will read disassembly cold, identify compiler patterns from Modules 04–17 in context, and reconstruct the original logic. This is the core skill of malware analysis, vulnerability research, and CTF binary challenges.

Prerequisites — All prior modules, especially Module 17 (compiler patterns) and Module 06 (control flow: jump tables, loops, conditionals).

What You Will Build

  • re_targets/cipher — stripped XOR cipher to reverse
  • re_targets/recursive — stripped recursive functions (TCO vs non-TCO) to reverse
  • re_targets/state_machine — stripped FSM to reverse
  • re_targets/crackme — stripped license validator: find the valid key from disassembly alone

The RE Workflow

  1. Static analysis — file, objdump -f, nm, strings: determine architecture, entry point, visible strings
  2. Disassembly — objdump -d -M intel or GDB layout asm: read the instruction stream
  3. Pattern recognition — identify known compiler patterns (see table below)
  4. Dynamic tracing — run under GDB with breakpoints, observe register values at key points
  5. Reconstruction — write pseudo-C from the assembly; verify by running the binary and matching output

The Four RE Targets

Target 1

cipher — XOR Stream Cipher

What to look for:

  • A loop with a counter (rdi or rcx incrementing)
  • xor byte [reg+counter], imm or xor byte, byte
  • A modulo pattern: and rcx, 3 (key length = 4 = power of 2) selecting a key byte
  • A constant loaded from .rodata — that constant is the key

Questions to answer: What is the key? How many bytes is it? Is it the same key for encrypt and decrypt?

Target 2

recursive — Sum-of-Squares and Fibonacci

What to look for:

  • A function that calls itself — or a jmp back to its own start (TCO)
  • Two argument registers: one decrements each iteration, one accumulates
  • Base case: test rdi, rdi / jz .return_acc
  • The non-TCO fib: two separate call fib instructions, result saved across the second call (must use a callee-saved register)

Questions to answer: Which function has TCO applied? What does the second argument accumulate?

Target 3

state_machine — HTTP Status Parser

What to look for:

  • A state variable — likely in a register kept across loop iterations
  • A central dispatch: cmp state, N / je .stateN chain, or a jump table (jmp [table + state*8])
  • Multiple transitions: mov state_reg, NEW_VALUE on each conditional path
  • Character class checks: sub al, 'A' / cmp al, 25 / jbe (is it A–Z?)

Questions to answer: How many states are there? Draw the transition diagram. What does the parser reject?

Target 4

crackme — License Key Validator

What to look for:

  • Length check: call strlen / cmp rax, 16 / jne .fail
  • Stride-4 loop: add rcx, 4 in loop increment — checks every 4th byte
  • Sum accumulation: add eax, [rdi+rcx] loop ending with cmp eax, 0x500
  • XOR checks: movzx eax, byte [rdi] / xor eax, [rdi+8] / cmp eax, 0x1F

Task: From the disassembly, extract all five constraints and find a 16-byte key that satisfies all of them simultaneously. Verify: ./re_targets/crackme <your-key>

Disassembly Walkthrough — Cipher Loop

; objdump -d -M intel re_targets/cipher output (approximate):
; Function at some address, no symbol name (stripped)

401130:  test   rsi, rsi            ; if (len == 0)
401133:  je     401160              ;   return;
401135:  xor    ecx, ecx            ; i = 0
401137:  lea    rdx, [rip+0xe62]   ; rdx = &KEY[] in .rodata
40113e:  nop    WORD PTR [rax+rax]  ; alignment nop
401140:  mov    eax, ecx            ; eax = i
401142:  and    eax, 3              ; eax = i % 4  (KEY_LEN=4, and 3 = mod 4)
401145:  movzx  eax, BYTE PTR [rdx+rax] ; eax = KEY[i%4]
401149:  xor    BYTE PTR [rdi+rcx], al  ; data[i] ^= key_byte
40114c:  inc    rcx                 ; i++
40114f:  cmp    rcx, rsi            ; i < len?
401152:  jne    401140              ; loop back
401154:  ret
Reading the cipher without source
From the disassembly above, you can determine: (1) There is a loop from 0 to len. (2) Each iteration XORs one byte of [rdi] with a value from a 4-element table at a fixed address in .rodata. (3) The table index is i & 3 — a repeating 4-byte key. To find the key: objdump -s -j .rodata re_targets/cipher and read the 4 bytes at the offset shown in the lea rdx, [rip+N] instruction. Those bytes are the key.

Exercises

Warm-up

1. Identify the XOR key from cipher disassembly

Run make disasm-cipher and find the lea rdx, [rip+N] instruction loading the key address. Calculate the absolute address (rip = address of the next instruction after the lea, plus the offset N). Then use objdump -s -j .rodata re_targets/cipher and read 4 bytes at that address. Verify by XOR-ing the first encrypted byte against key[0] and checking that you recover 'H' (0x48, first byte of "Hello, Reverse Engineer!").

Core

2. Solve the crackme

Disassemble re_targets/crackme with make disasm-crackme. Without reading target_crackme.c, identify all validation conditions from the disassembly. Write them down as constraints. Construct a 16-byte key satisfying all constraints — you may use Python or a small brute-force script to find one. Verify: ./re_targets/crackme <your-key> should print VALID KEY!. Only then read the source to confirm your analysis was correct.

Stretch

3. Reconstruct C pseudocode for the state machine

Disassemble re_targets/state_machine. Draw a state transition diagram with numbered nodes and labeled transitions (what input character causes each transition). Write C pseudocode for the FSM from your diagram alone — do not read the source. Then compare your pseudocode against target_state_machine.c. Score yourself: how many states did you identify correctly? How many transitions? Any you missed indicate blind spots in your pattern vocabulary to study further.

What's Next — Module 20: Bare-Metal Runtime

Module 20 builds a minimal runtime from scratch in pure assembly: a _start entry point that initializes the heap, a bump allocator, a write wrapper, and a no-libc exit. The resulting binary has no C runtime dependency at all — just the kernel ABI. This is the foundation for writing minimal implants, embedded firmware loaders, or understanding exactly what happens between execve and main.
