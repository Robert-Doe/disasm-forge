Arithmetic & the ALU

add, sub, mul, div, imul, idiv, adc, sbb — and exactly which flag each instruction sets, and when a result silently wraps.

Prerequisites — Modules 01–03: registers memorised, data directives understood, two's complement fluent.

  • The correct setup for div and idiv (a very common source of bugs)

The ALU Has No Concept of "Type"

The ALU is a pure bit-manipulation engine. When you execute add rax, rbx, the CPU adds 64 bits to 64 bits and writes 64 bits back. It has no idea whether those bits represent a signed integer, an unsigned integer, a pointer, or a packed byte array. You choose the interpretation. The only feedback the CPU gives you is the flags register — a set of status bits that record properties of the result (was it zero? did it produce a carry? did it overflow a signed range?).

This is why the same add instruction serves both signed and unsigned addition. The bits are the same; the interpretation differs. The flags let you detect problems regardless of interpretation.

add, sub, inc, dec, neg

add  rax, rbx       ; rax = rax + rbx  (sets CF,ZF,SF,OF,PF)
add  rax, 42        ; rax = rax + 42   (immediate operand)
sub  rax, rbx       ; rax = rax - rbx  (CF set if borrow needed)
inc  rax            ; rax++  — does NOT affect CF (unlike add rax,1)
dec  rax            ; rax--  — does NOT affect CF
neg  rax            ; rax = 0 - rax  (two's complement negation)
Gotcha — inc does not affect CF
inc rax does not set the Carry Flag even if rax wraps from 0xFFFFFFFFFFFFFFFF to 0. This is intentional (it allows inc inside a loop without disturbing a carry from a previous add), but it surprises many programmers. If you need CF after incrementing, use add rax, 1 instead.

mul and imul — Multiplication

x86-64 has two multiply instructions: mul (unsigned) and imul (signed). They differ in how they handle the sign of the result and which flags they set.

One-operand mul (unsigned, full 128-bit result)

; mul src  multiplies rax by src
; Result goes into rdx:rax  (upper 64 bits in rdx, lower 64 in rax)
mov  rax, 0xFFFFFFFFFFFFFFFF  ; 18446744073709551615
mov  rbx, 2
mul  rbx                      ; rdx:rax = 0x0000000000000001_FFFFFFFFFFFFFFFE
; rdx = 1  (high half)
; rax = 0xFFFFFFFFFFFFFFFE  (low half)

Two-operand and three-operand imul (signed, truncated)

imul rax, rbx          ; rax = rax * rbx  (result truncated to 64 bits)
imul rax, rbx, 6       ; rax = rbx * 6    (three-operand: compiler favourite)
Why compilers love three-operand imul
The three-operand form imul dst, src, imm is non-destructive — it computes src × imm without modifying src. This makes register allocation much simpler for the compiler. You will see it constantly in disassembly, often used for index calculations like imul rax, rcx, 24 to multiply an index by the size of a struct.

div and idiv — Division

Division is the most dangerous arithmetic instruction to get wrong. Before calling div or idiv, you must set up both rdx and rax as a pair — together they form the 128-bit dividend.

InstructionSetupQuotientRemainder
div rbxxor rdx,rdx (zero the high half)raxrdx
idiv rbxcqo (sign-extend rax into rdx)raxrdx
; Unsigned division: 100 / 7 = 14 remainder 2
mov  rax, 100
xor  rdx, rdx    ; REQUIRED: clear the upper half of the dividend
mov  rbx, 7
div  rbx         ; rax=14, rdx=2

; Signed division: -100 / 7 = -14 remainder -2
mov  rax, -100
cqo              ; sign-extend: if rax<0, rdx=0xFFFFFFFFFFFFFFFF
mov  rbx, 7
idiv rbx         ; rax=-14, rdx=-2
Division by Zero = #DE Exception
If the divisor is zero, or if the quotient doesn't fit in rax (e.g., dividing a large 128-bit number where the quotient exceeds 64 bits), the CPU raises a Divide Error exception (#DE). The OS delivers this as SIGFPE on Linux or as an exception on Windows. Your program terminates. There is no flag for this — you must validate before dividing.

adc and sbb — Multi-Precision Arithmetic

adc (Add with Carry) and sbb (Subtract with Borrow) let you chain arithmetic operations across multiple registers to work with numbers wider than 64 bits.

; 128-bit addition: (rdx:rax) += (rcx:rbx)
add  rax, rbx    ; add low halves; CF=1 if carry out
adc  rdx, rcx    ; add high halves PLUS the carry from the low half
; adc is: rdx = rdx + rcx + CF

CF vs OF — Two Different Kinds of Overflow

FlagMeaningRelevant interpretationExample
CFCarry / BorrowUnsigned overflow0xFFFF...FFFF + 1 → 0, CF=1
OFSigned OverflowSigned overflow0x7FFF...FFFF + 1 → negative, OF=1

The CPU sets both flags after every arithmetic instruction. You choose which one to check based on whether you care about unsigned or signed semantics. Module 06 shows the conditional jump mnemonics that test each flag.

Exercises

Warm-up

1. Verify the 128-bit multiply

Multiply 0xFFFFFFFFFFFFFFFF × 0xFFFFFFFFFFFFFFFF using mul. The exact result is 0xFFFFFFFFFFFFFFFE_0000000000000001. Print both rdx (high) and rax (low) and verify this.

Core

2. Integer division with remainders

Compute these in assembly and print quotient and remainder for each: (a) 255 / 16, (b) 1000 / 7, (c) -99 / 10 (signed). Verify the signed case: in C, -99 / 10 = -9 with remainder -9. Does your asm match?

Core

3. Trigger CF and OF separately

Write two sequences: one that sets CF=1 but OF=0, and one that sets OF=1 but CF=0. After each add, use pushfq + pop rax to capture rflags. Check bit 0 (CF) and bit 11 (OF) of the value to confirm which flag was set.

Stretch

4. 256-bit addition

Extend the multi-precision demo to add two 256-bit numbers stored across four 64-bit registers each. Use add for the lowest pair and adc for the remaining three pairs.
