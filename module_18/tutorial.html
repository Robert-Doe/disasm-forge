Stack Exploitation & Mitigations

The whole course distilled into one attack: a buffer overflow overwrites the return address and redirects rip to attacker-controlled code. Then each mitigation — stack canary, NX, ASLR, RELRO — raises the bar, and each bypass teaches you why the mitigation design made that bypass possible.

Prerequisites — Module 07 (call/ret, stack frame), Module 14 (ELF sections), Module 15 (mmap/mprotect), Module 16 (GOT/PLT). This module requires Linux.

The Stack Frame at RET

When vulnerable_copy() executes ret, the CPU does pop rip: it loads the 8 bytes at [rsp] into the instruction pointer. If an overflow has placed the attacker's address at that location, execution jumps there.

rbp+16 →
return address (8 bytes)
← overwrite target
rbp+8 →
saved rbp (8 bytes)
← overwrite step 2
rbp-63 →
char buf[64]
← overwrite step 1
rsp →
(bottom of buf)

Total bytes to overwrite before the return address: 64 (buf) + 8 (saved rbp) = 72 bytes.

The Payload Structure

# gen_payload.py output:
payload = b'A' * 72             # fills buf + overwrites saved rbp
        + struct.pack('# 8-byte LE return address

# When strcpy copies this into buf[64]:
#   buf[0..63]  = 0x41 × 64   (fill the 64-byte array)
#   buf[64..71] = 0x41 × 8    (overwrite saved rbp — value doesn't matter)
#   buf[72..79] = &secret_function in little-endian
#
# When ret executes:  pop rip → rip = &secret_function
Little-Endian and the Return Address
x86-64 stores multi-byte values with the least significant byte at the lowest address. An address like 0x0000000000401234 is stored as the bytes 34 12 40 00 00 00 00 00. Python's struct.pack('<Q', addr) produces exactly this byte order. When the CPU reads 8 bytes from [rsp] during ret, it reconstructs the original address. If you forget little-endian order and write the bytes in the opposite order, ret will jump to a completely different — and probably unmapped — address, causing a segfault instead.

Mitigations — Mechanism and Bypass

Stack Canary
-fstack-protector
A secret random value placed between the local variables and the saved rbp. Checked at function exit — abort if changed. Inserted by the compiler as mov rax, fs:0x28; mov [rbp-8], rax.
Bypass: leak the canary value via a format string or read primitive, then include the correct canary bytes in the payload so the check passes. Or: overwrite data before the canary (if target struct is before buf).
NX / DEP
-z noexecstack
Stack and heap pages are non-executable (no PROT_EXEC). The CPU refuses to execute code on those pages. Controlled by the GNU_STACK ELF program header flags.
Bypass: Return-Oriented Programming (ROP) — chain small existing code snippets ("gadgets") ending in ret. No new code is injected; existing executable pages are reused.
ASLR
sysctl randomize_va_space=2
The OS randomizes the load address of the binary (if PIE), stack, heap, and shared libraries each run. The attacker cannot know the address to overwrite with.
Bypass: information leak — read an address from a known location (e.g., via format string %p, or GOT entry visible through another primitive) to compute the ASLR slide, then calculate target addresses at runtime.
RELRO
-z relro -z now
Full RELRO: the linker resolves all PLT symbols at load time, then marks the GOT read-only. Writing to a GOT entry (classic technique for redirecting function calls) causes a segfault.
Bypass: target a different writable function pointer — __malloc_hook, __free_hook, C++ vtables, or FILE* function pointer tables in libc's I/O structures.
PIE
-pie
Position-Independent Executable: the binary itself is loaded at a random base address (not just libraries). Code addresses in the .text section are not predictable.
Same as ASLR bypass: leak a code pointer to determine the binary's base, then compute gadget addresses as base + known offset.

Stack Canary at the Instruction Level

; Compiler inserts at function entry (with -fstack-protector-strong):
    mov    rax, QWORD PTR fs:0x28   ; load thread-local secret from TLS
    mov    QWORD PTR [rbp-8], rax    ; store canary just above return addr
    xor    eax, eax

; And at function exit:
    mov    rax, QWORD PTR [rbp-8]    ; reload canary
    xor    rax, QWORD PTR fs:0x28   ; compare with expected
    jne    __stack_chk_fail            ; abort if different
    leave
    ret

Exercises

Warm-up

1. Confirm the 72-byte offset with GDB

Build vuln-unsafe. Run under GDB: gdb ./vuln-unsafe. Break at vulnerable_copy, then info frame to see the saved rip address. Compute saved_rip_addr - buf_addr and verify it equals 72. Then break at the ret instruction and observe x/gx $rsp — initially it holds the legitimate return address. Step once more to watch rip change.

Core

2. Observe canary protection in action

Build vuln-safe (stack canary enabled). Run the same overflow payload against it. You should see: *** stack smashing detected ***: terminated. Then run make asm-canary to generate the annotated assembly and find the fs:0x28 pattern. Count the exact instructions between the canary store and check — this is the window an attacker would need to bypass. Verify that with the canary present, even a correct return address in the payload does not help because __stack_chk_fail aborts before ret.

Stretch

3. Build a 3-gadget ROP chain (NX bypass)

With NX enabled (-z noexecstack) but ASLR off and no canary, build a ROP chain that calls secret_function without needing an executable stack. Use ROPgadget --binary vuln-unsafe --rop or objdump -d vuln-unsafe | grep -B1 ret to find a pop rdi; ret gadget. Then construct a chain: [padding × 72] + [gadget addr] + [arg] + [secret_function addr]. This demonstrates that NX alone — without ASLR — only raises the difficulty slightly when the binary contains usable gadgets.
