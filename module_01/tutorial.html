Toolchain Setup & Your First Assembly Program

Install NASM and GCC, understand the assemble→link→run pipeline, and write a program that the CPU executes instruction by instruction.

Prerequisites — This is the first module. You need a computer running Windows 10/11 (with MSYS2 installed or being installed now) or Linux x86-64. No prior assembly knowledge required.

What You Will Build

  • A working NASM + GCC toolchain on your machine
  • hello.asm — a 64-bit assembly source file with correct sections and a proper stack frame
  • print_helper.c — a tiny C helper so we can print without touching platform syscalls yet
  • A Makefile that assembles and links on both Linux and Windows (MSYS2) with a single make
  • A working binary that prints Hello, Assembly! and exits cleanly

Why Learn Assembly in 2025?

Every program that runs on your computer — whether written in Python, Rust, Go, or C — eventually becomes a sequence of machine instructions that the CPU fetches and executes one by one. Assembly language is the human-readable form of those machine instructions. Every high-level abstraction — functions, loops, objects, memory safety — compiles down to assembly.

As a security professional you regularly encounter situations where high-level source code is unavailable: reverse engineering malware, analysing crash dumps, writing exploits, auditing compiled binaries, understanding how mitigations like ASLR and NX work, or figuring out exactly what a compiler-generated binary does vs what the source code says it does. In every one of these situations, fluency in assembly is the difference between guessing and knowing.

This course teaches x86-64 assembly — the instruction set used by every Intel and AMD processor in desktop computers, servers, and most laptops made since 2003. When you can read and write x86-64 assembly, you can read any compiled binary produced by GCC, Clang, MSVC, or Rust's codegen backend. You can trace exactly what happens when a buffer overflows, understand why a ROP chain works, and see what an EDR hook looks like at the instruction level.

The goal is not to write production programs in assembly (compilers usually do a better job). The goal is to understand exactly what is happening inside the machine — because that understanding makes you a dramatically better security researcher, reverse engineer, and software developer.

The Assemble → Link → Run Pipeline

When you write C, a compiler translates your source into machine code in one step. With assembly, the process is separated into two explicit phases — and understanding each phase is essential.

Phase 1: The Assembler (NASM)

The assembler reads your .asm source file and produces an object file (.o or .obj). An object file contains binary machine code, but it is not yet a runnable program. It contains unresolved symbols — names like puts or printf that your code refers to but whose actual memory addresses are not yet known. The object file is a building block, not a finished product.

Phase 2: The Linker (ld via gcc)

The linker takes one or more object files and combines them into a single executable. It resolves all the unresolved symbols by finding their definitions — either in other object files you provide, or in system libraries like libc.so. The linker writes the final executable with all addresses filled in and the correct file format for your operating system (ELF on Linux, PE on Windows).

Insight
The two-phase pipeline is why you can have a program split across many .asm and .c files that all refer to each other — each file is assembled or compiled independently into an object file, then the linker connects them all. Module 16 explores this in full detail.

Phase 3: The Loader (the OS)

When you run your executable, the operating system's loader reads the file, creates a new process, maps the program's code and data into virtual memory, resolves any remaining dynamic library references, and transfers control to the entry point. From that moment, the CPU is executing your instructions directly. There is no interpreter in between.

Anatomy of an Assembly Source File

An assembly source file is divided into sections. Each section tells the assembler (and later the linker and loader) how a region of bytes should be treated. The three sections you will use in almost every module are:

SectionPurposePermissions at runtime
.textExecutable instructions — your codeRead + Execute (no write)
.dataInitialised global variables and string literalsRead + Write (no execute)
.bssUninitialised global variables (zeroed at load time)Read + Write (no execute)

The separation of permissions is not cosmetic — it is a security mechanism. Code lives in .text which is not writable; data lives in .data/.bss which is not executable. This is NX (No-Execute), and it is enforced by the CPU's memory management unit. You will attack and defend this boundary in Module 18.

Warning
NASM defaults to 16-bit mode for historical compatibility with old DOS programs. In 64-bit code you must put bits 64 at the top of every file, or NASM will silently misassemble your 64-bit instructions and your program will crash in mysterious ways.

The Stack Frame: Why We Push rbp

Every function in x86-64 assembly follows a ritual at its start and end. You will see it thousands of times, so understand it now.

The CPU has a register called rsp (the stack pointer) that points to the top of the call stack — a region of memory used for temporary storage and function call bookkeeping. When you call a function, the CPU pushes the return address onto the stack and jumps to the function. When the function returns, the CPU pops that address back and jumps to it.

The convention is that each function also saves the previous frame's base pointer (rbp) and sets rbp to point to its own frame base. This creates a linked list of stack frames that debuggers like GDB use to show you a backtrace. Without this, GDB cannot walk the call stack.

; Standard function prologue — appears at the start of every function
main:
    push rbp          ; save caller's frame pointer on the stack
    mov  rbp, rsp    ; our frame base = current top of stack
    ; ... function body ...
    pop  rbp          ; restore caller's frame pointer
    ret               ; pop return address into rip and jump to it

Code Walkthrough: hello.asm

; hello.asm — every line explained

bits 64             ; REQUIRED: tell NASM we are generating 64-bit instructions

extern print_hello ; declare that this symbol is defined somewhere else (print_helper.c)
                    ; the linker will resolve it — NASM just needs to know it exists

section .text       ; everything below goes into the executable code section
    global main     ; export 'main' so the linker (and C runtime) can find our entry point

main:               ; label — this address becomes the value of the symbol 'main'
    push rbp        ; stack frame prologue: save the previous base pointer
    mov  rbp, rsp  ; rbp now points to our frame base

    call print_hello ; push rip+5 onto stack, then jump to print_hello's address
                    ; the C runtime will handle argument setup, puts() call, etc.

    xor  eax, eax  ; return value = 0. Writing to eax zeros the upper 32 bits of rax too.
                    ; xor reg,reg is the canonical way to zero a register (1 byte shorter than mov)
    pop  rbp        ; restore caller's frame pointer
    ret             ; pop saved return address into rip → jumps back to C runtime
                    ; the C runtime then calls exit() with our return value (0)

Code Walkthrough: print_helper.c

/* print_helper.c
 * A C bridge so hello.asm can print without knowing the platform ABI yet.
 * The ABI teaches us how to pass arguments in registers — that's Module 09.
 */
#include <stdio.h>

void print_hello(void)       /* 'void' params = no arguments accepted */
{
    puts("Hello, Assembly!"); /* puts() writes the string + newline to stdout */
}

Toolchain Installation

Windows (MSYS2 — Recommended)

MSYS2 gives you a Linux-like shell with a proper package manager (pacman) on Windows. It is the easiest way to get a working NASM + GCC + GDB environment.

  1. Download and run the MSYS2 installer from msys2.org
  2. Open the MSYS2 UCRT64 terminal (not MSYS, not MINGW32)
  3. Update the package database:
    $ pacman -Syu
  4. Install the toolchain:
    $ pacman -S mingw-w64-ucrt-x86_64-nasm mingw-w64-ucrt-x86_64-gcc mingw-w64-ucrt-x86_64-gdb make
  5. Verify:
    $ nasm --version
    NASM version 2.16.x
    $ gcc --version
    gcc (Rev1, Built by MSYS2) 13.x.x
Tip
Always use the UCRT64 environment (not MINGW64, not MSYS). UCRT64 uses the Universal C Runtime which is the modern Windows standard. The package prefix is mingw-w64-ucrt-x86_64-.

Linux (Ubuntu / Debian)

$ sudo apt update && sudo apt install nasm gcc gdb make

Linux (Fedora / RHEL)

$ sudo dnf install nasm gcc gdb make

Build & Run Instructions

$ cd module_01
$ make
nasm -f elf64 -o hello.o hello.asm
gcc -Wall -Wextra -std=c11 -g -c -o print_helper.o print_helper.c
gcc -Wall -Wextra -std=c11 -g -no-pie -o hello hello.o print_helper.o
$ ./hello
Hello, Assembly!
$ echo $?
0

On Windows (MSYS2) the output and commands are identical, except the binary is named hello.exe and the format flag becomes win64.

Inspecting the Object File

Before linking, look at what the assembler produced:

$ objdump -d -M intel hello.o

You will see the raw machine code bytes next to the disassembled instructions. The call instruction will show an address of 0x0 — that is the unresolved symbol. After linking, run objdump -d -M intel hello and the address will be filled in.

Insight — Security Relevance
The gap between the object file (unresolved symbols) and the linked binary (addresses filled in) is where relocation happens. This is also how PLT/GOT hooking works — malware and EDRs alike can intercept function calls by patching the GOT entries that the linker fills in. Module 16 shows this in detail.

Running Under GDB

$ gdb ./hello
(gdb) break main
(gdb) run
(gdb) layout asm
(gdb) layout regs
(gdb) stepi
(gdb) stepi

layout asm shows the disassembled instructions. layout regs shows all registers. stepi executes exactly one instruction at a time. Watch rsp decrease by 8 when push rbp executes, and watch rbp change when mov rbp, rsp executes. This is assembly at the finest granularity.

Exercises

Warm-up

1. Confirm the pipeline

Run make and then make clean. Then manually run each step of the pipeline yourself:

  1. nasm -f elf64 -o hello.o hello.asm (or win64 on Windows)
  2. gcc -Wall -Wextra -std=c11 -g -c -o print_helper.o print_helper.c
  3. gcc -no-pie -o hello hello.o print_helper.o
  4. ./hello

Understand what each command produces. Run file hello.o and file hello and compare the descriptions.

Core

2. Modify the message

Change print_helper.c to print your name instead of "Hello, Assembly!". Rebuild and verify. Then add a second call to a new function print_goodbye() in hello.asm: declare it with extern print_goodbye, define it in print_helper.c, and call it after print_hello. Make sure the stack frame is still correct (rbp saved and restored, return value 0).

Core

3. Trace in GDB

Open the binary in GDB with gdb ./hello. Set a breakpoint at main: break main. Run it. Enable both layouts: layout asm, then layout regs. Step through every instruction with stepi. For each instruction, note what register or memory location changed and by how much. Pay particular attention to rsp during push/pop/call/ret.

Stretch

4. Return a non-zero exit code

Change the xor eax, eax to mov eax, 42. Rebuild and run ./hello; echo $?. Confirm you see 42. Now explain: why does writing to eax set the return value when the C runtime reads rax? (Hint: look up what happens to the upper 32 bits of rax when you write to eax — this is covered fully in Module 02.)

Stretch

5. Read the object file

Run objdump -d -M intel hello.o and then objdump -d -M intel hello. Find the call instruction in both outputs. In the object file, what address does it call? In the linked binary, what address does it call? Run nm hello and find the address of print_hello. Do the numbers match? This is the linker's symbol resolution in action.
