What Is an ABI?

An Application Binary Interface (ABI) is the contract between separately compiled pieces of code. It specifies: which registers carry function arguments, which register carries the return value, which registers a function is allowed to destroy, how the stack must be aligned, and how structs are passed and returned. If two pieces of code use different ABIs, they cannot interoperate — arguments land in the wrong registers, the stack gets corrupted, and the program crashes in ways that are nearly impossible to debug without knowing the ABI.

x86-64 has two dominant ABIs. They are not compatible. Every time you write assembly that interfaces with C code, you must know which ABI is in use.

rsi and rdi are CALLEE-SAVED on Windows
On Linux, rsi and rdi are caller-saved (used as argument registers). On Windows, they are callee-saved. A function that uses rsi/rdi on Windows must push them at entry and pop them before return. Linux asm code ported to Windows that uses rsi/rdi as scratch registers will silently corrupt the caller's values. This is one of the most common ABI porting bugs.

The Windows Shadow Space

The Microsoft x64 ABI requires the caller to allocate 32 bytes of "home space" (also called "shadow space") immediately before calling any function. The callee may use these 32 bytes to spill its first four register arguments for debugging or for stack-based access. The caller does not need to fill these bytes — just allocate the space.

; Windows: calling a function with 5 arguments
sub  rsp, 40          ; 32 shadow + 8 for arg5 (keep 16-byte alignment)
mov  qword [rsp+32], 5  ; arg5 lives above the shadow space
mov  rcx, 1            ; arg1
mov  rdx, 2            ; arg2
mov  r8,  3            ; arg3
mov  r9,  4            ; arg4
call some_function
add  rsp, 40          ; release shadow + arg5 space

Floating-Point Arguments

Both ABIs pass floating-point arguments in xmm0–xmm3 (Windows) or xmm0–xmm7 (Linux). For variadic functions, the System V ABI requires setting al to the number of xmm registers used, so the callee knows how many to save.

; Load doubles into xmm0-xmm3 and call a C function
movsd  xmm0, [rel val1]   ; first double arg
movsd  xmm1, [rel val2]   ; second double arg
mov    al, 2              ; System V: 2 xmm registers used (variadic callee)
call   c_function
Security Insight — ABI in Exploit Development
When writing shellcode or ROP chains that call Windows API functions, you must follow the Microsoft x64 ABI exactly: allocate 32 bytes of shadow space, pass args in rcx/rdx/r8/r9, preserve rsi/rdi/rbx/r12–r15. A ROP chain that calls VirtualProtect without providing shadow space will crash inside the function when it tries to spill its arguments. This is why shellcode often sets rsp to a predictable location before calling APIs — to ensure the shadow space is always available.

Conditional Assembly for Cross-Platform ABI

; abi.asm — handle both ABIs in one file
%ifdef WIN64
    mov  rcx, 1     ; arg1 on Windows
    mov  rdx, 2     ; arg2 on Windows
%else
    mov  rdi, 1     ; arg1 on Linux
    mov  rsi, 2     ; arg2 on Linux
%endif
call some_function

; Makefile passes -DWIN64 on Windows, nothing on Linux
; nasm -f win64 -DWIN64 abi.asm   (Windows)
; nasm -f elf64         abi.asm   (Linux)

Exercises

Warm-up

1. Verify argument register order in GDB

Break at the entry of c_seven_args in GDB. Print all registers: info registers. On Linux, confirm that rdi=1, rsi=2, rdx=3, rcx=4, r8=5, r9=6, and that the 7th argument (7) is on the stack at [rsp+8] (above the return address). On Windows, confirm rcx=1, rdx=2, r8=3, r9=4 with args 5–7 on the stack.

Core

2. Call printf directly from assembly

Write an asm function that calls the C printf function with a format string and two integer arguments. On Linux: format in rdi, args in rsi/rdx, al=0. On Windows: format in rcx, args in rdx/r8. Ensure the stack is 16-byte aligned before the call and the shadow space is allocated on Windows.

Stretch

3. Verify callee-saved xmm registers on Windows

On Windows, xmm6–xmm15 are callee-saved. Load a known value into xmm6 in main, call a C function that uses xmm registers internally, then read xmm6 back using movsd [rsp-8], xmm6; mov rax, [rsp-8] and print it. It should be unchanged. Then write a C function that deliberately doesn't preserve xmm6 and observe the corruption.
