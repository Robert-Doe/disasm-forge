Control Flow Is Just Manipulating rip

In the fetch-decode-execute cycle, the CPU reads the instruction at the address in rip, executes it, and advances rip to the next instruction. Control flow works by changing what rip points to. An unconditional jmp overwrites rip with a new address. A conditional jump does the same — but only if certain flags are set.

This is why controlling rip is the goal of almost every code-execution exploit. Buffer overflows overwrite the saved return address (which gets loaded into rip by ret). ROP chains control rip by placing fake return addresses on the stack. If an attacker can write an arbitrary value into rip, they control the program. Module 18 makes this concrete with a live exploit.

cmp and test

Neither cmp nor test store a result — they exist solely to set flags for the conditional jump that follows.

cmp  rax, rbx   ; computes rax - rbx, sets CF/ZF/SF/OF, discards result
cmp  rax, 0     ; compare with immediate

test rax, rax   ; computes rax & rax, sets ZF/SF/PF, discards result
                 ; canonical "is rax zero?" — ZF=1 means zero
test rax, 0x80  ; "is bit 7 set?" — ZF=0 means yes
Tip — test reg,reg vs cmp reg,0
test rax, rax and cmp rax, 0 both set ZF based on whether rax is zero. test is preferred because it is one byte shorter (no immediate operand) and cannot affect CF or OF (making it safer in multi-instruction sequences that chain flag checks). Compilers always emit test for the "is value zero?" check.

Critical: Signed vs Unsigned Jumps
After cmp rax, rbx, choosing jl vs jb is critical: jl (signed less) checks SF≠OF; jb (unsigned below) checks CF=1. For the values 200 (unsigned) and -56 (signed), both are 0xFFFFFFFFFFFFFFC8 — the CPU cannot tell which you intend. You must choose the right jump. Using the wrong one is the source of "signed/unsigned comparison" bugs that can be weaponised.

Translating C Control Structures to Assembly

if / else if / else

; C: if (r12 > 0) { ... } else if (r12 == 0) { ... } else { ... }
    cmp  r12, 0
    jg   .is_positive    ; signed greater
    je   .is_zero
    ; else falls through here
    ; ... negative code ...
    jmp  .done
.is_positive:
    ; ... positive code ...
    jmp  .done
.is_zero:
    ; ... zero code ...
.done:

while loop

; C: while (rax > 0) { use(rax); rax -= 3; }
.while_top:                  ; condition check at top
    cmp  rax, 0
    jle  .while_done       ; exit if rax <= 0
    ; ... loop body ...
    sub  rax, 3
    jmp  .while_top
.while_done:

for loop (count down — preferred in assembly)

; C: for (int i = 5; i > 0; i--) { use(i); }
    mov  rcx, 5
.for_loop:
    ; ... loop body using rcx ...
    dec  rcx
    jnz  .for_loop        ; jump back while rcx != 0
; Counting DOWN is preferred: the terminal condition (== 0) is free from dec,
; so no separate cmp instruction is needed. Saves one instruction per iteration.

switch via jump table

; A jump table is an array of code addresses in .data
section .data
    jump_table  dq case_0, case_1, case_2, case_3, case_4

section .text
    cmp  r13, 4
    ja   .default           ; unsigned: handle out-of-range

    lea  rbx, [rel jump_table]
    mov  rbx, [rbx + r13*8]  ; load address: table[index] (each entry = 8 bytes)
    jmp  rbx                  ; jump to the case handler
Security Insight — Jump Tables in Exploits
Jump tables are a target in exploitation. If an attacker can write to the jump table (a writable .data section), they can redirect any switch dispatch to arbitrary code. This is why production compilers place jump tables in .rodata (read-only) and use RIP-relative offsets rather than absolute addresses. When you see a jump table in disassembly during malware analysis, check whether it is in a writable section — that may indicate intentional obfuscation or a vulnerability.

Exercises

Warm-up

1. Trace the jump table

Run objdump -d -M intel control. Find the jmp rbx instruction and the jump_table symbol. Set a breakpoint in GDB at the jmp rbx instruction and run with r13=2 (modify the register with set $r13=2 before stepping). What address does rbx hold? Use x/i $rbx to confirm it points to case_2.

Core

2. Implement a do-while loop

A do-while loop places the condition check at the bottom: the body always runs at least once. Implement: do { print(rax); rax++; } while (rax < 5);. Note that the condition check at the bottom means you don't need a jmp to get back to the top — the conditional branch does both jobs.

Core

3. Signed vs unsigned: spot the difference

Set rax = 0xFFFFFFFFFFFFFFFF (which is -1 signed and 18446744073709551615 unsigned). Compare it with 0 using cmp rax, 0. Then branch with both jg .big and ja .big. Which branch is taken? Why? Confirm in GDB by checking which path executes.

Stretch

4. FizzBuzz in assembly

Implement FizzBuzz for 1–20 entirely in assembly: for each number, print "Fizz" if divisible by 3, "Buzz" if divisible by 5, "FizzBuzz" if both, else print the number. Use div or idiv with 3 and 5, check rdx (the remainder), and use conditional jumps to decide which string to print.
