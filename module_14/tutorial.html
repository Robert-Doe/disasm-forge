ELF & PE Binary Formats

Machine code lives inside containers. ELF (Linux) and PE (Windows) tell the OS loader where to put each section in memory, where the entry point is, and which shared libraries to link. Exploit development, binary patching, shellcode injection, and writing your own loader all start here.

Prerequisites — Module 03 (sections: .text, .data, .rodata, .bss), Module 09 (linker output, extern declarations).

What You Will Build

  • elf_reader.c — parses an ELF64 binary: header, section headers, program headers, symbol table
  • pe_reader.c — parses a PE32+ binary: DOS/COFF/Optional headers, section table, data directories

Why Binary Format Knowledge Matters for Security

Every technique in exploit development touches binary formats:

  • Shellcode injection — you place raw bytes into a writable section and redirect rip into it. The page permission flags are in ELF program headers / PE section characteristics.
  • ROP chains — you need gadget addresses, which are virtual addresses determined by ImageBase + section RVA + byte offset within the section.
  • Binary patching — changing an instruction requires finding its file offset from the section's PointerToRawData + the instruction's offset within the section.
  • Import hooking — redirecting a function call requires locating the Import Address Table (IAT) in the PE Data Directories and patching the function pointer.
  • ASLR bypass — PIE ELF binaries have type ET_DYN; the base address randomized by the OS loader is added to all relative virtual addresses. Leaking a code pointer gives you the base.

ELF Format

File Layout

An ELF file has four regions in order:

  1. ELF Header (64 bytes) — magic, class, ABI, entry point, offsets to section and program header tables
  2. Program Header Table — describes memory segments (one per LOAD entry, mapped into virtual memory by the OS loader)
  3. Sections — the actual content: code, data, symbols, strings, relocations
  4. Section Header Table — metadata about each section (name, type, address, offset, size, flags)

Program Header — Segments vs Sections

Sections are for the linker; segments are for the loader. A LOAD segment describes a contiguous range of the file to be mapped into virtual memory at a given address with given permissions (R/W/X). Typically:

  • First LOAD segment — .text + .rodata, permissions R--X
  • Second LOAD segment — .data + .bss, permissions RW-
  • GNU_STACK segment — permissions specify whether the stack is executable (RWX = vulnerable, RW- = NX enabled)
Security Insight — NX Stack
The GNU_STACK program header controls whether the process stack is executable. If its flags include PF_X (execute), the kernel marks the stack pages executable, allowing classic shellcode injection. Modern binaries compiled without -z execstack have GNU_STACK as RW-. When auditing a binary for exploitability, check this header first.

PE Format

ELF Structure

  • ELF Header (64 bytes)
  • Program Header Table (segments)
  • Section content
  • Section Header Table
  • Sections identified by name (.text, .data…)

PE Structure

  • DOS Header (64 bytes) + DOS stub
  • PE Signature "PE\0\0"
  • COFF Header (machine, section count)
  • Optional Header (entry point, image base, data dirs)
  • Section Table
  • Section content

PE Key Addresses

TermMeaning
ImageBasePreferred load address (0x400000 for EXE, 0x180000000 for DLL)
RVA (Relative Virtual Address)Offset from ImageBase. VA = ImageBase + RVA
File offsetByte position in the PE file on disk
VA (Virtual Address)Address in the process's virtual address space

Data Directories

The Optional Header contains 16 data directory entries, each with an RVA and size. Critical ones for security analysis:

IndexNameSecurity relevance
0Export TableFunctions exported by DLLs; target of DLL hijacking
1Import TableFunctions imported from other DLLs; target of IAT hooking
5Base RelocationASLR patch table — if missing, no ASLR
9TLS TableThread-local storage callbacks; execute before main() — abused by packers
12IATImport Address Table — patched by loader/hookers
Parser Security — Bounds Check Everything
Both elf_reader.c and pe_reader.c in this module omit bounds checks on offsets for readability. A production binary parser must validate every field before dereferencing: e_shoff + e_shnum * e_shentsize <= filesize, sh_offset + sh_size <= filesize, etc. Malformed files fed to unchecked parsers have produced dozens of CVEs in tools like binutils, file, and antivirus engines. Adding bounds checks to both readers is exercise 2 below.

Exercises

Warm-up

1. Map file offset to section name

Extend elf_reader.c with a function const char *section_at_offset(uint8_t *buf, Elf64_Ehdr *eh, uint64_t file_offset) that returns the name of the section containing a given file offset. Test it by passing the file offset of the entry point instruction: compute entry_point_va - text_section_sh_addr + text_section_sh_offset. This is the operation disassemblers perform to map virtual addresses to file content.

Core

2. Add bounds checking to both parsers

Add a helper static int check_range(long fsize, uint64_t off, uint64_t size) that returns 0 if off + size > (uint64_t)fsize. Call it before every pointer cast in both readers. If a check fails, print an error and exit. Test with a truncated binary: dd if=./elf_reader of=./truncated bs=1 count=128. The readers should now exit cleanly with an error rather than segfaulting or reading garbage.

Stretch

3. Locate and dump the .text section bytes

In elf_reader.c, after printing all section headers, find the .text section, use sh_offset and sh_size to locate its bytes in the buffer, and print the first 64 bytes as hex (8 bytes per row). Verify by comparing against objdump -d ./elf_reader | head -20. You have just implemented the core of a hex dump tool identical to how Ghidra and IDA load binary content.
