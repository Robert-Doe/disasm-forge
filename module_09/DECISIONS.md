# DECISIONS.md — Module 09: Calling Conventions & the ABI

## Decision 1: Use %ifdef WIN64 conditional assembly for platform differences

**Decision:** A single `abi.asm` file handles both ABIs using NASM's `%ifdef WIN64` preprocessor conditional, with the Makefile passing `-DWIN64` on Windows.
**Why:** Maintaining two `.asm` files (one per platform) doubles the maintenance burden and prevents the student from seeing the two ABIs side by side. Conditional assembly keeps the diff visible — the student can read both branches and understand exactly what changes. This is the same technique used in production cross-platform libraries.
**Trade-off:** For very large projects, platform-specific files are often cleaner than deeply nested conditionals. The Linux kernel uses separate arch directories; Windows drivers use separate build targets. The single-file approach works well for small to medium modules.

## Decision 2: Demonstrate the Windows shadow space by laying out the stack explicitly

**Decision:** The Windows ABI section comments show the exact stack layout with byte offsets for each argument slot.
**Why:** The "shadow space" (32 bytes the callee may use to spill its register arguments) confuses almost every programmer encountering Windows calling convention for the first time. Seeing `[rsp+0]` through `[rsp+48]` with labels forces the student to compute the offsets themselves and understand why `sub rsp, 64` is needed (32 shadow + 24 for 3 stack args + 8 for alignment).
**Trade-off:** Production Windows code generated by MSVC often keeps the shadow space permanently allocated in the caller's prologue (not re-allocated per call), which differs from the demo. The demo allocates once in main's prologue and reuses it.

## Decision 3: Set al = number of xmm args for the variadic convention

**Decision:** `mov al, 4` is set before calling `c_float_args` even though the C prototype is not variadic.
**Why:** The System V ABI requires that `al` (the low byte of `rax`) contains the number of xmm registers used when calling a *variadic* function. Setting it for non-variadic functions is harmless but teaches the habit. A bug where `al` is not set before calling a variadic function like `printf` causes crashes only on some microarchitectures (the callee may check `al` to decide how many xmm regs to save).
**Trade-off:** On Windows, `al` has no such role — the xmm argument count is fixed by the prototype. The Windows variadic convention uses the normal integer registers for all variadic args.

## Decision 4: Return a C struct to demonstrate the rax:rdx two-value return

**Decision:** `c_return_pair` is a C function returning a `struct { uint64_t lo; uint64_t hi; }`.
**Why:** The System V ABI maps a struct of two 64-bit integers to `rax` (first field) and `rdx` (second field) — no memory copying, no hidden pointer. This is an important ABI detail: small structs are returned in registers, not on the stack. Returning a C struct forces the compiler to emit the register-based return, which the student can verify with `gcc -S`.
**Trade-off:** A struct larger than 16 bytes (two 64-bit fields) is returned via a hidden first argument — the caller passes a pointer in `rdi`/`rcx` to memory the callee fills in. Module 11 covers struct layout and the hidden-pointer convention.
