Data Representation & Memory Fundamentals

How values are stored in memory, why bytes appear reversed, how negative numbers work, and how the four memory sections differ — with live hex dumps proving every claim.

Prerequisites — Modules 01 & 02 complete: toolchain working, registers understood, zero-extension rule memorised.

What You Will Build

  • data.asm — defines values using every data directive (db/dw/dd/dq) in all four sections, then hex-dumps them live
  • data_demo.c — C helpers that print raw memory as hex bytes
  • Fluency with little-endian byte order, two's complement, IEEE 754 bit layout, and section permissions

Why Data Representation Matters for Security

Every vulnerability class you will ever encounter ultimately comes down to a mismatch between how a programmer thinks a value is represented and how the CPU actually stores it. Integer overflow bugs happen because the programmer forgot that a 32-bit unsigned value wraps at 4,294,967,295. Type confusion bugs happen because the programmer read a float's bit pattern as an integer or vice versa. Buffer overflows happen because the programmer misunderstood the byte layout of a struct. Sign confusion bugs — where a signed comparison produces unexpected results — happen because two's complement negatives look like large positive numbers when treated as unsigned.

This module removes all ambiguity. You will define values in memory, dump them as raw bytes, and observe exactly how the CPU lays them out. No abstractions. No assumptions. Just bytes.

Memory Sections and Their Permissions

When the OS loads your program, it maps different parts of the binary into virtual memory with different permissions. These permissions are enforced by the CPU's Memory Management Unit (MMU) — violating them raises a hardware exception (segfault / access violation).

Security Insight — NX and W^X
The rule that writable memory is not executable (and vice versa) is called W⊕X (Write XOR Execute) or NX/DEP. It is a hardware-enforced mitigation against shellcode injection. If an attacker overflows a buffer and injects shellcode into the stack or heap, the CPU will refuse to execute it because those regions are marked non-executable. Module 18 (Stack Exploitation) shows exactly how this protection is implemented and what Return-Oriented Programming does to circumvent it.

Data Directives: Defining Values in Memory

NASM provides directives that let you embed data directly into your binary at a specific section and offset. The directive name indicates the width of each value:

DirectiveWidthExampleBytes produced
db1 bytedb 0x4141
dw2 bytesdw 0x123434 12
dd4 bytesdd 0xDEADBEEFEF BE AD DE
dq8 bytesdq 0x010203040506070808 07 06 05 04 03 02 01

Notice the bytes are always reversed in memory. This is little-endian byte order — the least significant byte comes first (at the lowest address). All x86 and x86-64 processors are little-endian.

Little-Endian Byte Order, Explained

When you write dw 0x1234, you might expect to see 12 34 in memory. But x86 is little-endian — the byte with the lowest value (least significant byte) comes first at the lowest address. So 0x1234 is stored as 34 at address N and 12 at address N+1.

N+0
34
LSB
N+1
12
MSB

When the CPU reads those two bytes back into a register using a mov ax, [N] instruction, it reassembles them correctly: ax = 0x1234. The byte reversal happens transparently during load and store.

Why This Trips Up Security Researchers
When you look at a hex dump of a packet, a binary file, or a memory region, the bytes are shown in memory order (little-endian). A 32-bit integer that logically is 0xDEADBEEF appears in a hex dump as EF BE AD DE. When writing exploits, crafting file format parsers, or interpreting network traffic, you must constantly translate between "logical value" and "bytes on the wire/disk". This confusion is the source of many off-by-one and byte-swap bugs.

Two's Complement: How Negative Numbers Work

The CPU does not have separate circuits for signed and unsigned arithmetic. It uses the same add and sub instructions for both. The trick is two's complement: negative numbers are represented so that addition wraps correctly.

To negate a number in two's complement: flip all bits, then add 1.

 1   in binary (8-bit):  0000 0001
~1 (flip all bits):      1111 1110
~1 + 1 = -1:            1111 1111  =  0xFF

 127 in binary (8-bit):  0111 1111  =  0x7F
-128 in binary (8-bit):  1000 0000  =  0x80   (the most negative 8-bit value)

The key insight is that the bit pattern 0xFF means 255 as unsigned and -1 as signed. The CPU doesn't know which you intend — you tell it by choosing signed vs unsigned instructions (jl vs jb, imul vs mul, etc.).

Security Insight — Signed/Unsigned Confusion
Many vulnerabilities arise from mixing signed and unsigned interpretations. A classic: a length field is read as int32_t, checked with if (len > MAX) (signed comparison — passes for negative values), then passed to memcpy which treats it as size_t (unsigned — now it's 4 billion bytes). This pattern appears in CVE-2021-3156 (sudo heap overflow), CVE-2018-5407, and hundreds more.

IEEE 754 Floating Point — The Bit Layout

A 32-bit float (dd 1.0) is stored as three fields packed into 32 bits:

FieldBitsFor 1.0Value
Sign310positive
Exponent30–2301111111 = 127Biased exponent: 127 - 127 = 0, so 2⁰ = 1
Mantissa22–0000...000Implicit leading 1, no fractional bits

So 1.0 as hex is 0x3F800000. In memory (little-endian): 00 00 80 3F. The hex dump in the program will confirm this.

Uninitialized Data: .bss

Variables in .bss are not stored in the binary file. The binary only records how many bytes of .bss space the program needs. The OS loader allocates that many zeroed pages and maps them into the process's virtual address space. This has two implications:

  • A 1 MB global array in .bss adds nearly zero bytes to the binary on disk
  • All .bss values are guaranteed to be zero at program start — no need to initialize them explicitly
Tip — resb vs db 0
Use resb N in .bss (reserve N uninitialized bytes). Do not use db 0, 0, 0... in .data just to get zeros — that wastes space in the binary. The distinction is: .data bytes appear in the binary file; .bss bytes do not.

Code Walkthrough: data.asm

; Defining data with directives
section .data

byte_vals  db 0x41, 0x42, 0x43, 0x44  ; 4 bytes: 41 42 43 44 ('A','B','C','D')
byte_count equ $ - byte_vals           ; $ = current position; result = 4

word_vals  dw 0x1234, 0x5678          ; 4 bytes: 34 12 78 56  (little-endian!)

dword_val  dd 0xDEADBEEF              ; 4 bytes: EF BE AD DE

qword_val  dq 0x0102030405060708      ; 8 bytes: 08 07 06 05 04 03 02 01

neg_one    dq -1                       ; 8 bytes: FF FF FF FF FF FF FF FF

float_one  dd 1.0                      ; 4 bytes: 00 00 80 3F (= 0x3F800000)

section .bss
bss_buf    resb 16                     ; reserve 16 bytes — OS will zero them

; Loading a qword from memory into a register:
section .text
    mov rax, [rel qword_val]         ; rax = 0x0102030405060708
                                        ; CPU reassembles little-endian bytes transparently

Exercises

Warm-up

1. Predict the hex dump

Before running, write down on paper what you expect the hex dump to show for dw 0xABCD and dd 0x00010203. Then add those two definitions to data.asm, hex-dump them, and check your predictions.

Core

2. Two's complement negatives

Add three more values to .data: dq -2, dq -256, dq -32768. Hex-dump each one. For each value, verify the result manually: take the absolute value, write it in binary, flip all bits, add 1, convert to hex. Does it match?

Core

3. Decode the IEEE 754 float

The hex dump of 1.0 is 00 00 80 3F. Reassemble the bytes in big-endian order: 3F 80 00 00 = 0x3F800000. Now extract the three fields: bit 31 (sign), bits 30–23 (exponent), bits 22–0 (mantissa). What is the exponent bias for 32-bit floats? What real exponent does the stored value represent? What is the implicit leading bit of the mantissa? Write out the mathematical formula and confirm it equals 1.0.

Stretch

4. Attempt a .rodata write (deliberately cause a crash)

Add a string label to .rodata. Then in the .text section, get its address into rdi and try to write a byte: mov byte [rdi], 0x41. Build and run. The program should crash with a segfault. Run it under GDB, catch the SIGSEGV, and use info signal and x/i $rip to identify the exact instruction that caused the fault. This confirms that .rodata permissions are enforced at the hardware level.

Stretch

5. Observe .bss in the binary vs at runtime

Run readelf -S data_demo (Linux) or objdump -h data_demo. Find the .bss section. Note its file size (should be 0) and its memory size (should be 17 — 16 bytes for bss_buf + 8 for bss_counter). This is the p_filesz vs p_memsz distinction that tells the loader "allocate this much zeroed memory even though there's nothing in the file for it."
