Capstone: Mini x86-64 Disassembler

You write a length-disassembler in pure assembly. Given a byte buffer, it identifies each instruction's length, opcode, ModRM/SIB structure, displacement, and immediate — then formats a disassembly listing. This is how every disassembler (IDA, Ghidra, objdump) works at its core.

Prerequisites — All prior modules. This capstone uses: register encoding (Mod 03), addressing modes (Mod 10), string ops (Mod 11), syscalls (Mod 15), linker/symbols (Mod 16), inline asm / C interop (Mod 17), RE methodology (Mod 19).

What You Will Build

  • capstone/disasm.asm — the disassembler engine in pure x86-64 assembly
  • capstone/disasm.h — C interface header (DisasmInsn struct, extern declarations)
  • capstone/main.c — test driver: opcode buffer, syscall sequence, length accuracy suite, self-disassembly

The x86-64 Instruction Encoding

Every x86-64 instruction is a variable-length byte sequence with up to six fields:

Legacy Pfx
0–4 bytes
66/67/F0/F2/F3
REX
0–1 byte
4x
Opcode
1–3 bytes
xx / 0F xx
ModRM
0–1 byte
mod/reg/rm
SIB
0–1 byte
scale/idx/base
Disp
0/1/4 bytes
Imm
0/1/2/4/8 bytes

A disassembler reads these fields left-to-right. The hard part: which fields are present, and how many bytes each field occupies, depends entirely on the opcode. There is no universal header. This is why x86-64 instruction encoding is famously complex — and why security researchers must understand it deeply.

REX Prefix — Extending the Register Space

The REX prefix (0x40–0x4F) was added in AMD64 to extend the original 8 integer registers to 16. It encodes four bits:

BitNameMeaning
REX.W (bit 3)W64-bit operand size (override default 32-bit)
REX.R (bit 2)RExtends ModRM reg field to access r8–r15
REX.X (bit 1)XExtends SIB index field to access r8–r15
REX.B (bit 0)BExtends ModRM r/m, SIB base, or opcode-embedded reg
 
; How to check REX bits in the disassembler:
test  r15, 0x08    ; REX.W — operand is 64-bit
test  r15, 0x04    ; REX.R — reg field +8
test  r15, 0x02    ; REX.X — SIB index +8
test  r15, 0x01    ; REX.B — r/m or base or opcode reg +8

The ModRM Byte

When an instruction has a register-or-memory operand (r/m), a ModRM byte follows the opcode. It encodes:

FieldBitsValues
mod7:600=indirect, 01=disp8, 10=disp32, 11=register
reg5:3Register operand (or opcode extension for groups)
r/m2:0Register or base-of-memory reference
 
; Extract ModRM fields:
movzx eax, byte [rbx + r14]   ; read ModRM
mov   cl, al
shr   cl, 6                     ; cl = mod
mov   bl, al
shr   bl, 3
and   bl, 7                     ; bl = reg
and   al, 7                     ; al = r/m

SIB Byte — Scaled Index Addressing

When r/m = 4 (RSP encoding) in mod != 11, a SIB byte follows. It enables [base + index*scale + disp]:

FieldBitsMeaning
scale7:6Multiplier: 00=×1, 01=×2, 10=×4, 11=×8
index5:3Index register (RSP encoding = no index)
base2:0Base register (RBP in mod=00 = disp32 only)

The SIB byte is why [rsp+8] in machine code looks different from [rbp-8] — RSP cannot serve as an index register, so the encoding for r/m=4 was repurposed to signal "SIB byte follows."

Displacement and Immediate Encoding

Displacements are sign-extended — an 8-bit -16 stored as 0xF0 becomes -16 in a 64-bit register via movsx. This is critical for correct branch target computation:

; Read disp8 and sign-extend to 32-bit:
movsx  eax, byte [rbx + r14]
mov    dword [r13 + INSN_DISP], eax
inc    r14

; CALL rel32 — the +5 accounts for the instruction's own length:
; target = instruction_addr + 5 + rel32
movsx  eax, dword [rbx + r14]
mov    dword [r13 + INSN_IMM], eax
add    r14, 4

Instruction Groups — The / Extension

Some opcodes are groups: a single opcode byte covers multiple instructions, with the actual instruction determined by the reg field of ModRM. These are written as opcode /N in the Intel manual:

Opcode/0/1/2/3/4/5/6/7
81ADDORADCSBBANDSUBXORCMP
F7TEST—NOTNEGMULIMULDIVIDIV
FFINCDECCALLCALL farJMPJMP farPUSH—
 
; Decode opcode group 81h:
movzx eax, byte [rbx + r14]   ; peek at ModRM (don't consume yet)
mov   cl, al
shr   cl, 3
and   cl, 7                     ; cl = reg field = subopcode
cmp   cl, 7
je    .it_is_cmp               ; /7 → CMP r/m, imm32

Two-Byte Escape: 0F Prefix

When the opcode byte is 0F, the next byte is the actual opcode. This doubling of the opcode space accommodates the many instructions added after the original 8086:

0F xxInstruction
0F 05SYSCALL
0F 0BUD2 (undefined — triggers #UD fault)
0F 40–4FCMOVcc r64, r/m64
0F 80–8FJcc rel32 (long conditional jumps)
0F 90–9FSETcc r/m8
0F AFIMUL r64, r/m64
0F B6/B7MOVZX r64, r/m8 / r/m16
0F BE/BFMOVSX r64, r/m8 / r/m16

The DisasmInsn Struct Layout

; Struct layout — must match disasm.h exactly:
; Offset   Size   Field
;    0       1    length        (total bytes consumed)
;    1       1    opcode        (primary opcode byte)
;    2       1    has_rex
;    3       1    rex
;    4       1    has_modrm
;    5       1    modrm
;    6       1    has_sib
;    7       1    sib
;    8       4    disp  (int32, sign-extended)
;   12       8    imm   (int64)
;   20       1    op_type  (OP_NONE/REG/IMM/MEM/REL)
;   21       3    padding
;   24      64    mnemonic[64]
;   88      64    operands[64]
; Total: 152 bytes
Why length matters most
A disassembler that gets any instruction's length wrong will lose sync — every subsequent byte it reads will be misaligned, producing garbage output for the rest of the function. Length computation is the one property that must be exact. Mnemonic formatting can be approximate; length cannot. This is why the test suite has a dedicated length accuracy case.

Security Application: Shellcode Analysis
A length-disassembler is the first building block of a shellcode scanner. To check whether a buffer contains a syscall instruction (0F 05), a sandbox needs to decode every instruction to find the opcode — scanning for 0F 05 bytes is insufficient because those bytes might appear as data inside a longer instruction's immediate field. The disassembler core you built here prevents that false-negative by correctly computing lengths first, then checking opcodes.

Exercises

Warm-up

1. Decode a raw ELF section

Use the ELF reader from Module 14 to locate the .text section of any compiled binary, extract the raw bytes, and pass them to disasm_decode in a loop. Print the first 30 instructions. Compare your output against objdump -d -M intel. How many instructions match exactly?

Core

2. Add PUSH/POP xmm register support (66-prefixed SSE2)

The legacy prefix 0x66 overrides operand size to 16 bits for integer ops, but also prefixes many SSE2 instructions (66 0F 58 = addpd). Extend the decoder to handle the 66 prefix: store it in a has_66_prefix field, and add cases for 66 0F 58 (addpd), 66 0F 59 (mulpd), 66 0F 57 (xorpd). Run your decoder against the simd.o from Module 13 and verify the SSE2 instructions decode correctly.

Stretch

3. Implement a simple control-flow graph builder in C

Using the disassembler as a library, write a C function build_cfg(uint8_t *code, size_t len, uint64_t base_addr) that: (1) starts at offset 0; (2) decodes each instruction and checks if it is an unconditional branch (JMP), conditional branch (Jcc), or RET/INT3/UD2; (3) adds the branch targets to a work queue; (4) traces all reachable code. Print a list of basic block entry addresses. Test it on the target_state_machine binary from Module 19 — your basic block list should match what Ghidra or objdump's control flow analysis produces.
